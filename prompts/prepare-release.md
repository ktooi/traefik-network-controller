# Prompt: prepare or publish a release

Prepare Traefik Network Controller for `<GitHub/GHCR, GitHub plus Docker Hub, or GitLab Registry>`. Target repository: `<confirmed URL or local checkout>`. Intended stable version: `<version>`. Scope: `<prepare only, or explicitly authorized tag/publication>`. Read `AGENTS.md`, `SPEC.md` PUB-001–004 and AC-19/AC-20, `docs/releasing.md`, the selected provider guide, `docs/licensing.md`, actual workflows and `TESTING.md`.

1. Inspect the current source, package/toolchain versions and local changes. Preserve unrelated work. Resolve the real repository/default branch/registry identities from evidence; do not invent account names or digest values.
2. Evaluate the reviewed dependency and Rust notices, license compatibility and original-contribution rights. Changes to dependencies/toolchain require a new review before regenerating notices. CI checks the result; it does not approve new licenses automatically.
3. Run `bash scripts/ci/check.sh` on capable Linux, keeping all socket tests. Run the image build/smoke on an explicitly selected disposable CI Engine. Separate observed passes, failures and unavailable gates; do not substitute pure tests for actual Docker or routed traffic.
4. Validate the intended stable tag with `python3 scripts/ci/release_metadata.py v<version>`. Confirm it identifies reviewed code on the protected default branch and that provider tag/environment/runner controls are in place. Inspect optional Docker Hub opt-in as an additional destination with its own result.
5. Keep credentials in the selected provider's secret store and use short-lived provider tokens where documented. Do not request or print secret values. Do not run unreviewed fork workflow code in a trusted parent context. GitLab jobs have platform-issued tokens even if the job contains no login command.
6. Complete authorized local preparation and show exact changes, required settings and unresolved evidence. Preserve existing user authorization; preparation alone does not authorize creating/pushing tags, registry publication, changing repository visibility, or deployment.
7. If publication is explicitly authorized and its prerequisites are satisfied, use a new non-forced version tag and inspect the resulting pipeline, each registry digest and visibility. Never claim a push succeeded from YAML alone. Avoid overwriting a published release during recovery; inspect partial registry results first.

Report the license decision and limits, destination, changed files, SPEC mapping, exact checks and outcomes, provider settings still needed, and verified artifact/digest URLs only when they exist. Publication does not update a running controller; deployment remains subject to its own existing authorization and operations procedure.
